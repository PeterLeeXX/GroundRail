# GroundRail

用事实让 Agent 落地，同时用最少轨道约束流程。

使用用户的语言；保留代码标识符、命令、路径和原始错误的原文。

## 宿主兼容

本 Skill 只使用 Agent Skills 标准的 `name`、`description` 和 Markdown 指令，不依赖宿主专属 frontmatter、hook、动态命令注入或固定工具名。同一份 `SKILL.md` 可由 Codex 和 Claude Code 加载：Codex 使用 `$groundrail` 显式调用，Claude Code 使用 `/groundrail`；两者都可根据 `description` 自动触发。

把 Researcher、Reviewer 和 Executor 视为职责，而不是固定的代理类型。优先使用宿主原生的独立上下文、子代理、搜索、读取、编辑和验证能力；能力名称不同时按职责映射。宿主无法提供独立上下文 Reviewer 时，遵循下文降级规则，不用同上下文自审冒充独立 Review。

## 核心契约

按 `Fact → Plan → Execute` 推进，进入后续阶段前完成前序阶段。阶段是逻辑门槛，不是文档仪式：低风险小任务可用几行内联 Fact 和 Plan；复杂、长时或跨会话任务才持久化工件。

| 用户目标 | 必经路径 |
| --- | --- |
| 调查、事实整理 | Fact |
| 原因解释或诊断 | Fact → Plan；在“证据支持的结论”中交付诊断 |
| 方案或计划 | Fact → Plan |
| 实施或修改 | Fact → Plan → Execute |
| 只读代码审查 | 最小 Fact 契约 → Code Review；Review 是横切动作，不伪装成 Execute |

复用用户已有工件：验证 `facts.md` 的来源并只补缺口；补齐最小 Fact 契约后直接 Review 已有计划或 diff，不重写已确认内容。不得把用户或其他 Agent 的摘要当成已验证事实。

让主 Agent 持有连续判断、冲突消解、Reviewer 仲裁和最终综合。仅把耗时研究、宽仓库扫描、独立假设、机械修改或独立验证等边界清楚的重活委派给子代理；小任务、强耦合链路和直接阻塞下一步的工作留在主 Agent。子代理默认只返回结果；除非获得排他的路径所有权，不得写工件或与其他 Agent 同时修改文件。

任务需要外部研究且宿主支持子代理时，尽早启动后台 Researcher，让主 Agent 同时继续不依赖研究结果的本地调查或准备工作。Researcher 必须：

- 只依据拥有该事实的一手来源调查问题，例如官方文档、规范、源码和第一方 API；每项结论追溯到原始出处，不用二手文章替代。
- 把发现写入单个 Markdown 文件，并在每项主张旁引用来源。
- 优先采用仓库已有研究笔记目录和命名；没有惯例时写入 `tasks/<task-slug>/research.md`，授予该文件排他写权限，并向用户报告实际路径。

研究结果是 Fact 输入，不是自动成立的结论。主 Agent 读取工件、核对它与本地证据的边界和冲突，再决定后续阶段；没有可并行工作或研究规模很小时直接由主 Agent 完成，不为形式启动子代理。

Reviewer 在触发时必须使用干净上下文。若宿主无法创建独立 Reviewer，可执行标为降级的只读隔离复查供参考，但它不满足强制检查点；停在当前门槛并向用户报告，不得冒充通过。

把需求含义、产品行为、范围、破坏性操作、成本、安全和不可逆选择留给用户；根据证据自主决定普通实现细节。修改代码或数据前，取得用户对已审计划的明确授权；用户预先明确授权“按审查后的计划执行”可覆盖后续实施。只读操作不需要修改授权。

## Fact

搜集所有需求相关的重要事实，不扩张到无关区域。覆盖适用的代码与调用、测试与运行行为、配置和数据、依赖与外部契约、异步状态、信任边界及 UI 行为。

根据风险选择能回答当前问题的最小充分证据：

| 风险信号 | Fact 的最小证据 |
| --- | --- |
| Bug、回归或性能问题 | 已运行且能命中用户症状的反馈信号；没有有效信号时保留缺口，不猜修复 |
| 外部 API、依赖或版本行为 | 实际版本、当前一手契约和聚焦验证 |
| UI 或浏览器问题 | 适用的真实 DOM、console、network、截图或交互结果 |
| 身份、权限、密钥、PII、支付或外部输入 | 信任边界、有效权限和敏感数据处理证据 |
| 重试、队列、缓存或批处理 | 进展性、终态和工作量边界 |

只有信号不足或范围扩大时才增加检查。调用专项 Skill 或工具时只采用其局部技术规则，仍以 GroundRail 作为顶层生命周期。

只把可观察、可定位、可复现的内容写入事实记录。为每项提供来源定位和必要验证；注明配置实际生效层级；数据库默认只读并隐藏敏感值。给“未找到”注明搜索路径、符号、数据范围或查询条件；把未知保留为证据缺口，不推断补齐。

事实记录不得包含诊断、方案或建议。主 Agent 可以基于事实形成工作结论，但必须把它放入 Plan 的“证据支持的结论”，与观察事实分开。

简单 Fact 在对话中内联。复杂、跨会话或用户要求留档时，优先使用用户指定路径，其次使用仓库既有任务文档惯例；都没有时使用 `tasks/<task-slug>/facts.md`。检查目标不存在或取得覆盖确认，写入后向用户报告路径。

Fact 的完成条件：关键事实有来源；否定结论有边界；证据缺口已列出；剩余未知不实质影响当前目标。作为独立交付物、已持久化或高风险的 Fact 必须通过 Fact Review；低风险内联 Fact 仅在继续进入 Plan 时可并入随后必做的 Plan Review，避免重复 Reviewer。

## Plan

只在 Fact 完成后开始。先消除会改变产品行为、范围、验收、成本、安全或不可逆状态的歧义；需求清晰时直接采用用户明确陈述，存在重大歧义时持续澄清并取得确认。不要把普通实现选择推回用户。

计划包含：目标、验收与非目标；引用 Fact ID 的诊断或设计结论；现有实现和复用点；按位置排列的行动步骤；最小充分验证；阻塞项和用户决策。优先复用并选择能完整满足目标的最小连贯改动。只有抽象能消除真实重复或建立有意义的边界时才引入；不为假想未来添加层次、包装或兼容结构，不粘贴大段代码。

Bug 计划必须说明反馈信号、证据支持的根因或待证伪假设，以及能防止回归的验证。根因尚未建立时，计划下一步调查，不假装进入修复。

低风险计划可内联。复杂、跨会话、将交给其他执行者或用户要求留档时，优先使用用户路径或仓库惯例；否则写入 `tasks/<task-slug>/plan.md`。不得覆盖未知文件；由主 Agent 负责落盘并报告路径。

完整 Plan 必须在稳定版本上通过 Plan Review。Reviewer 同时核对未单独审查的内联 Fact。用户已有计划时只修复已接受的问题，不为统一格式重写。Plan 是目标时在 Review 后交付；实施时在 Review 后取得授权。

只有新事实实质影响需求、验收、范围或所有权、可行性、安全、数据或外部契约时才返回 Fact。局部符号和复用细节可直接以源码定位补入计划。

## Execute

以已审且获授权的 Plan 为执行边界。主 Agent 默认实施；仅在改动边界独立、文件所有权清楚且验证明确时委派 Executor。向委派者提供计划、仓库根目录、仓库指令、范围、非目标、验证命令和停止条件。

- 按小而连贯的增量实施，优先复用现有实现，保持改动最小且可回滚。
- 不顺手重构或扩大范围；记录真实命令与结果，不把未运行、失败或不适用写成通过。
- 实施后检查所有触达代码，删除此次改动引入且没有实际收益的间接层、包装器、helper、兼容层和推测性泛化。只简化触达区域，除非用户明确要求更广泛重构。
- 发现实质新事实时返回 Fact；仅需重大改变方案时返回 Plan。实质修订后的 Plan 必须重新 Review，旧授权随之失效；仅当用户的预先授权明确覆盖该类修订时无需再次确认。
- 在代表性 diff 和相关验证形成稳定整体后启动 Code Review，不在每次保存后触发。

实施完成要求计划范围已实现、风险对应验证已运行，且没有未解决或未决的 P0/P1：`needs-context` 必须补证后重新分类，影响执行边界的 `user-decision` 必须取得用户决定；只有有充分证据的 `reject` 不阻塞。只读审查的完成条件是报告已交付，不要求代码无问题，也不得未经授权修复。

## Review

Review 不是阶段。仅在稳定工件上自动启动干净上下文 Reviewer：独立交付、持久化或高风险 Fact，完整 Plan，或代表性代码差异。仅被读取的 README、AGENTS、源码文档和空白模板不触发。

给 Reviewer 一个最小完整契约包：原始需求与确认、审查类型和边界、工件、相关事实与来源、仓库根目录和指令、允许读取的相关及相邻源码范围、验证结果。不要传主 Agent 的结论。允许 Reviewer 在范围内打开引用和相邻代码；干净上下文不等于贫乏上下文。

按四轴检查：

- Contract / Intent：是否真正满足需求、Plan、验收、范围和用户决策边界。
- Correctness/Safety：逻辑、边界、回归、安全和数据完整性。
- Repository Shape / Code health：是否复用现有内容、符合仓库惯例，并避免不必要的复杂度、重复、耦合、范围蔓延和无收益抽象。
- Verification：证据是否真实、能命中行为、覆盖声明范围。

非平凡改动在宣布完成前，必须对稳定 diff 给出明确的 Intent 与 Code health 结论。发现问题时只修正授权范围内的触达区域，并在实质变化后复审。

严重级别：P0 为阻塞、重大逻辑、安全或数据问题；P1 为重要缺陷、明确风险、遗漏或重复造轮子；P2 为低影响鲁棒性或风格问题，最多三项。

使用以下 Reviewer Prompt：

```text
对抗性只读审查。依据 CONTRACT 判断 ARTIFACT 会在哪里失败；不要总结或修改。
可在给定仓库范围内读取引用及相邻代码。只报告有证据、可执行的问题。
每项输出：严重级别、审查轴、位置/证据、影响、最小修复方向、置信度。
若无问题，明确说明未发现 P0/P1。Fact Review 另列已覆盖面、未覆盖面及其是否阻止目标阶段。
```

Reviewer 输出是证据，不是裁决。主 Agent 必须逐项核对并分类：`accept`、`reject`、`needs-context`、`user-decision`，说明理由。修复已接受且位于授权范围内的 P0/P1；P2 默认只报告，仅在已审授权范围覆盖、收益明确且不扩张范围时选择性处理。只读 Review 只报告，不修复。

工件实质修改后再按同类型复审；不要复审未变化版本。同一问题再次出现时，仅在下一步没有新证据或只能猜测性扩张范围时停止并报告。

## 工件最小结构

```markdown
# Facts — <task>
- 需求与搜索边界：
- F-01：<观察>｜<来源>｜<验证>
- N-01：<有边界的否定结果>（按需）
- G-01：<证据缺口及影响>（按需）

# Plan — <task>
- 已确认需求、验收、非目标：
- 证据支持的结论：<结论 → Fact ID>
- 复用点：<现有对象与位置>
- 步骤：<位置｜行动｜验证>
- 阻塞项或用户决定：
- 修改授权：<仅实施时>
```

## Handoff

当用户要求交接、任务需要由新会话继续或当前会话必须在未完成状态停止时，把当前对话的必要续接信息写成一个 Markdown 交接文档：

- 保存到用户操作系统的临时目录，而不是当前工作区；使用宿主提供的临时目录解析方式，并报告绝对路径。
- 概述当前状态、剩余目标、已作用户决定、阻塞项和下一步；若用户为交接提供了参数，把它们视为下一会话的重点并据此裁剪内容。
- 添加 `Suggested skills` 小节，使用精确 skill 名称说明下一 Agent 应调用哪些 Skill；没有则写 `None`。
- 不复制 specs、plans、ADRs、issues、commits、diffs、研究或事实工件中已有的内容；改为引用其路径、提交或 URL。
- 隐去 API key、密码、令牌、个人身份信息及其他敏感值；路径中含敏感身份信息时也要泛化。

交接文档只用于续接，不替代 Fact、Plan、Review 或最终交付物。

## 交付

只说明与本次目标相关的完成内容、工件路径、实际验证、适用的 Review 仲裁、未解决风险和所需用户决定。实施中若作出计划未明确且会影响公共契约、数据形态、依赖、存储或并发策略的重要决定，简要列出；没有则不增加占位说明。不得用推测填补证据缺口，也不得把未运行的验证写成已通过。
